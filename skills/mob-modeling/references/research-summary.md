# 조사 요약 (2026-11, 왜 이렇게 하나)

근거: 오픈소스 도구·제작 기준·ModelEngine 제한·자동화와 AI·보유 몹 67종 수치 조사. Mojang 공식 수치 기준은 없다
→ 공통 규칙은 커뮤니티 가이드·엔진 문서에서, 스타일은 **프로젝트가 고른 기준 몹에서** 뽑는다(2층 구조).

## 1. 무엇이 "따로 놀아" 보이게 하나
- 해상도(텍셀 밀도)는 대부분 이미 같다: 67종 중 55종이 인게임 16 px/블록. 차이는 **칠하는 방식(명암 폭·면 테두리·밝기)과 큐브 밀도**.
- 다만 밀도가 튀는 소수(56.5·33·31 또는 5.3·8.9 px/블록)는 한 화면에서 가장 먼저 눈에 띈다 → 1순위.
- 텍스처만 다시 칠해서는 형태가 단순한 몹이 촘촘한 몹처럼 보이지 않는다 → 형태 보강(부품)이 필요하다.
- 판매처는 판매자 사이의 스타일 일관성을 보장하지 않는다. 여러 판매자의 팩을 섞는 서버는 들여온 뒤 맞추는 단계를 직접 가져야 한다.

## 2. 분업
| 작업 | 맡는 쪽 | 한계 |
|---|---|---|
| .bbmodel 읽기·수정, 4.x·5.0 둘 다 | 코드 | Blockbench 에 명령줄 모드가 없어 JSON 을 직접 다룬다 |
| 엔진 규칙·1층·2층 검사 | 코드 (`lint.py`) | "보기 좋은가"는 못 판단 |
| 촘촘한 텍스처 밀도 낮추기 | 코드 → 사람 | 1~2px 디테일 손실 → 손질 목록 |
| 성긴 텍스처 밀도 올리기 | 코드는 정수배 격자·1px 구조만 | 1.2~1.8배 어긋남은 다시 그리기(사람·GPT) 또는 예외 |
| 명암·테두리·위 밝음 | 코드가 만들고 사람이 승인 | 상징색 지키기 (`--protect`) |
| 라인업·동작 확인 렌더 | 코드 | |
| 기존 뼈 안에 큐브 부품 더하기 | 코드 초안 → 사람 판정 | 디자인 감각이 사람 수준이라는 근거 없음 |
| 컨셉 시트·재질 견본 | GPT (사용자 경유) | 시안 고르기는 사람 |
| 커스텀 몹 UV 텍스처를 AI 로 통째 | 하지 않음 | AI 는 면별 UV 배치를 모름 |
| AI 3D 메시 → 큐브 몹 | 참고 그림까지 | 고밀도·리깅 불가·라이선스(Hunyuan3D 는 한국 적용 제외) |

## 3. 프로젝트가 정할 것 (정하기 전 기본값)
| 결정 | 기본값 |
|---|---|
| 기준 몹과 프로필 수 | 가장 자주 보이는 몹 계열로 프로필 1개부터, 필요하면 2~3개 |
| 텍셀 밀도 | 16 px/블록 (바닐라) |
| 레이드급 보스 예외 | 키 10블록 넘는 보스만 밀도 8 이상까지 |
| 회전 규칙 밖 큐브 판정 | 인게임 확인 전까지 경고 |
| 외부 GitHub 코드 실행(헤드리스 Blockbench 등) | 하지 않음 (승인 받으면 두 번째 의견으로만) |

## 4. 구매할 때
- 판매처의 "16x" 표기는 1차 필터일 뿐 → 받으면 바로 `lint.py` + 라인업. Hytale 겸용 모델은 32 px/블록일 수 있다.
- 보는 것: ModelEngine 4 이상, MythicMobs 설정 동봉, 밀도, 동작 수(일반 5·보스 12 이상), VFX 모델 별도, 요구 버전.
